## Defect and remediation

The original client form had no explicit method. Before its React submit handler attached, native browser submission could use GET and serialize named credentials into a URL. Application code that prevents default submission after hydration cannot protect that earlier window.

The shared login, registration and verification form now has `method="post"`. A hydration snapshot keeps inputs, password visibility controls and the submit button disabled in server HTML and during initial hydration. The submit handler prevents default and also requires readiness before processing values. Once hydrated, the existing SDK-based sign-in, sign-up and resend behavior remains intact. With JavaScript disabled, the controls remain disabled; this patch does not add a separate server-side authentication flow.

The POST fallback provides a second boundary: even when a test deliberately enables inputs and invokes the browser's native submit method without React, values are sent in the request body rather than its query string. This fallback is not presented as a working login endpoint.

No form values, FormData, passwords or provider responses are logged by the form. Existing service error sanitization is unchanged. The remediation prevents future native-form GET leakage; it does not rotate passwords or remove previously exposed data from browser history or old logs.

## Development origins and logging

Development request logging omits login, registration, verification and Auth callback/confirmation URLs, which can contain sensitive one-time parameters. Other request logging remains enabled. Next.js documents this setting as development-only.
